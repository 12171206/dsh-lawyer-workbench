### 包里已经有一套"办案操作系统"，只是没有界面

`27-工具/legal-work-control`（法律工作总控）不是普通技能，是**规则层**，它定义的东西恰好就是工作台的数据模型：

- **事项工作区协议**：`律师工作目录/诉讼/民事/<客户>/<案件>/01-客户材料 … 08-归档` + `_系统记录/当前事项.md`、`总索引.md`、`诉讼案件总览.md`、`期限台账`
- **交付物硬闸门**：草稿 / 律师内部报告 / 提交法院客户 / 飞书 / 图片 / 修订稿 / Word 七类，各有必过链路
- **Word 链路**：`出稿前审查(PASS) → draft.html → html_to_docx.py → health_check.py`；要素式起诉状走模板克隆填充
- **质量闸门**：完整读取 → 关键数据提取 → 读取复查摘要；法规核验（北大法宝）→ 法规校验摘要；来源边界记录；OCR 校正
- **语义路由表**：78 行"用户这么说 → 走哪个技能"的映射（可直接当工作台的按钮映射表）
- **复盘台账 + 飞书**：交付后回写

也就是说：**做界面不是重新设计工作流，是把已经写好的协议变可见、可变点击。**

## 二、四个关键判断（这决定方案长什么样）

### 1. 217 个技能直接铺在左侧 = 灾难，必须先分级

- 150 个是社区英译中包，里面重复出现 3 类"脚手架技能"（`cold-start-interview` / `customize` / `matter-workspace`，每个赛道抄一遍，约 40 个），还有 `claim-chart`、`deposition-prep`、`privilege-log`、`legal-hold`、`DSAR` 这类英美程序概念；
- 对中国诉讼律师：噪音 > 价值；对涉外/法务：有参考价值。
- **结论**：左栏只放 67 个中文实务技能（再精选 25 个高频），150 个折叠进"社区参考库"，并打"非中国法、仅供参考"标。

### 2. 全量装技能会吃掉 1.7 万 tokens 常驻上下文，而且会跟工作台抢事权

- DSH 的技能目录是常驻系统提示的；217 条描述 ≈ 1.7 万 tokens；
- 40 个 `cold-start-interview` 之类同名技能会互相冲突、争着当入口；
- **结论：不装，改成"目录化 + 按需加载"**——左栏点一下，把 `SKILL.md` 的绝对路径 + 一行任务写进会话，模型读完即用。系统提示成本≈0，加载还更精准。

### 3. 律师的入口不是工具名，是"我手上这个案子到哪一步、今天该做什么"

- 技能名是 `contract-review`、`litigation-doc-drafting`，律师记不住也不该记；
- 包里的 `lawyer-case-workbench`（阶段流水线）+ `25-诉讼流程` 21 个技能本身就是按阶段切的；
- **结论：主轴 = 案件/事项 + 阶段 + 期限；技能降级为"阶段里的动作按钮"。**

### 4. 硬闸门会被律师当成"卡住"，界面上必须变成进度条

出稿前审查、法规核验、来源边界、飞书终检会在很早就拦截。直接暴露成"报错"律师就不用了。**进度条化**：每份文书显示 4 态（草稿 → 已审 → 已导出 → 已交付），未过的显示"差哪一步"而不是"失败"。

## 三、方案：左栏工作台 + 案件模式（两者组合，不是二选一）

你提的两个方向其实是一套东西的两半：**左栏解决"去哪"，案件模式解决"在里面怎么干活"**。

```
┌ 左栏 56px ────┬ 第二栏 320px ──────────┬ 主区 ─────────────────────┐
│ ▣ 案件台       │ 案件列表（按期限风险排）│ 对话 / 或 案件模式三栏     │
│ ⌘ 业务台       │ 或 业务线分类树         │                           │
│ ▤ 文书台       │                         │                           │
│ ⏰ 期限台      │                         │                           │
│ ⚙ 律师画像     │                         │                           │
└───────────────┴─────────────────────────┴───────────────────────────┘
```

### 3.1 左栏 5 个入口（对应 DSH 的 `sidebar.panellist`）

| 台 | 第二栏内容 | 主区内容 |
|---|---|---|
| **▣ 案件台**（主入口） | 案件卡片：客户/案由/阶段进度条/下一节点倒计时/未完成清单数；顶部"新案子"3 步向导（客户→案由→程序类型）；筛选：期限风险、阶段、最近活动 | 点开案件 → 进入**案件模式** |
| **⌘ 业务台** | 12 条业务线（民事/刑事/劳动/破产/合同/常法/合规…），每条线一张"能力地图"：阶段 → 动作 → 技能 | 技能抽屉卡 + "一键开跑" |
| **▤ 文书台** | 四列看板：草稿 / 已审 / 已导出 / 已交付（对应包里硬闸门） | 文书预览 + 出稿审查/导出按钮 |
| **⏰ 期限台** | 今日 / 本周 / 剩余 30 天三档 | 期限详情 + 关联文书/动作 |
| **⚙ 律师画像** | 执业领域、风险偏好、工作目录、常用模板 | 对应 `practice-profile.md` |

### 3.2 12 个工作台（技能按律师场景重排，不按技术目录）

包里是按 `21-刑事 / 22-劳动 / 23-破产 / 24-合同 / 25-诉讼 / 26-合规 / 27-工具` 的技术目录切的，律师看不懂。重排成 12 台：

| # | 工作台 | 典型动作 | 挂载技能 |
|---|---|---|---|
| 1 | 接待咨询 | 首次接待、微信快答、沟通笔录、服务建议书 | legal-consultation-assistant、case-communication-log、preliminary-legal-analysis、case-materials-to-docx |
| 2 | 案件管理 | 建档、进展更新、期限台账、组合总览、结案归档 | lawyer-case-workbench、lawyer-case-progress、litigation-case-management、case-intake-and-retainer、case-closing-and-archiving |
| 3 | 证据 | 取证方案、证据目录、三性审查、质证、保全/调查令 | lawyer-evidence-handling、evidence-investigation-management、litigation-analysis-tools |
| 4 | 法律研究 | 请求权分析、法条类案检索、法源核验、论证自检 | lawyer-legal-research、statute-and-case-search、lawyer-source-verify、lawyer-legal-reasoning |
| 5 | 诉讼策略 | 争议焦点、胜负评估、庭审提纲、调解底线 | lawyer-litigation-analysis、case-discussion-outline、pre-trial-preparation |
| 6 | 文书 | 起诉状/答辩状/代理词/律师函、判决书、审理报告 | lawyer-doc-drafting、litigation-doc-drafting、civil-judgment-document、trial-report |
| 7 | 庭审 | 庭前准备、庭审纪要、庭后代理词、复盘 | pre-trial-preparation、trial-and-post-trial |
| 8 | 合同 | 审查（含 Word 红线）、起草、委托合同、续约提醒 | lawyer-contract-review、contract-review、contract-drafting、retainer-contract-management |
| 9 | 可视化 | 时间轴/关系图/争点树/证据链（Mermaid→PNG） | litigation-visualization |
| 10 | 刑事 | 侦查/审查起诉/一审/二审/速裁/未检/死刑/特殊程序 | criminal-* ×7 + special-procedures + simplified-fast-track |
| 11 | 劳动·破产 | 仲裁、经济补偿、用工合规；破产 8 角色 10 程序 | labor-* ×5、bankruptcy-* ×10 |
| 12 | 合规·工具 | 广告/食品/产品/监管监测；格式转换、去 AI 味、出稿审查、模板导出 | 26-* ×4、27-* ×8 |

> 00 的 9 个 `lawyer-*` 是**横向质量层**（推理自检、法源核验、合规闸门），不单独成台，而是每个台交付前都要过。

### 3.3 新形态：案件模式（Case Mode）

注册一个 conversation view，选中案件后会话区变三栏：

```
┌ 案件骨架 260px ──┬ 对话（现有 chat） ────────┬ 产出 & 期限 300px ─┐
│ 客户 / 案由       │                           │ 本阶段产出物        │
│ 对方 / 程序类型   │  （自动注入案件上下文：    │  草稿 / 已审 / …    │
│ ● 当前阶段        │    当前事项.md + 材料索引）│ 期限倒计时          │
│ ☑ 阶段 checklist  │                           │ 材料缺口 3 项       │
│ 下一节点 11-15    │  [ 下一步 ▾ ]             │ 交付清单            │
└──────────────────┴───────────────────────────┴────────────────────┘
```

**核心交互是"下一步"按钮**：每个阶段自动算 3 个候选动作（来自 `routing-map.md` + 阶段映射），点一下就把「技能 + 案件上下文 + 目标产物类型」拼成一句话发到会话。律师全程不需要知道技能叫什么名字。

例如案件在"立案后"阶段，右栏提示"举证期限剩 3 天"，点「下一步 → 证据目录」：

> 用 `lawyer-evidence-handling` 处理案件 `诉讼/民事/张三诉李四借款/`，输出证据目录（分组文本段落式），当前事项已在 `_系统记录/当前事项.md`。

## 四、技术落地（DSH 里怎么做）

### 4.1 一个插件，两个半边

`@local/dsh-lawyer-workbench`，结构直接照抄工作区已有的 `plugins/dsh-topic-library`（已验证可用：注册了 `sidebar.panellist` + `main` 面板）：

```
plugins/dsh-lawyer-workbench/
  package.json        dsh.bundle.patch + dsh.client.inject
  cordis.patch.yml    insert 一个插件 entry，config: { 工作目录, catalog 路径, 飞书开关 }
  index.js            Host 半：service + agent tools
  client.js           Client 半：sidebar.panellist 图标 + main 面板 + conversation view
  locale/{zh,en}.json icon.svg
```

- **Host 半**暴露：`cases.list()` / `case.get()` / `case.nextActions()` / `catalog()` / `deliverable.setStatus()`，读工作目录下的真实文件；同时注册 agent tools `case_open` / `case_next` / `case_advance`，让模型和界面共用同一套状态（而不是各记一份）。
- **Client 半**：`sidebar.panellist`（左栏图标）→ `main`（keyed 面板）；P1 再加 `conversation.view`（案件模式）和 `settings.section`（律师画像）。

### 4.2 技能装载策略（三选一，我建议 B）

| | 做法 | 常驻成本 | 风险 |
|---|---|---|---|
| A 全量装 | 217 个拷进 `~/.dsh/skills/` | ≈1.7 万 tokens | 同名技能冲突、英美法误用、律师被 217 个名字淹没 |
| **B 精选 + 目录按需（推荐）** | 只装 9 个 `lawyer-*`（已装）+ 12 台各 1 个总入口 ≈ 21 个；其余点击时读 `SKILL.md` | ≈1k tokens | 需要维护 catalog 与路径 |
| C 纯目录 | 不装技能，只做导航 | 0 | 模型仍需读技能文件，等价于 B 但少入口技能 |

### 4.3 两个必须先解决的坑

1. **路径断链**：包内技能硬引用 `skills/legal/legal-work-control/references/*.md`、`skills/legal/.../templates/...`。装到 `~/.dsh/skills/` 后这些路径不存在 → 技能"嘴上说有规则、文件找不到"，会大量假装执行。
   → 解决：建 `~/.dsh/skills/legal/` 共享目录 + 装完跑路径重写脚本；或把 `legal-work-control/references` 复制到每个技能目录旁。
2. **DSH 技能目录是扁平的**（一层一个 SKILL.md），而包是 `分类/技能/` 两层。→ 安装时拍平，并同步改写内部相对引用。

### 4.4 依赖现状

- ✅ python-docx / openpyxl / Pillow / lxml 都有（bundled python）
- ✅ 插件脚手架、locale、icon 有现成样板（`plugins/dsh-topic-library`、`plugins/dsh-jianying-batch`）
- ⚠️ 北大法宝 MCP 未接通 → 法规核验类按钮先标"未接通（用网页检索兜底）"
- ⚠️ 飞书 CLI 依赖账号态，包里 4 处写"飞书正式交付物"，先做成可选

## 六、风险与对策

| 风险 | 对策 |
|---|---|
